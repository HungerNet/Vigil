## 1. Audit

### 1.1 The formats

All are JSON written by `core/json` (insertion-ordered objects, exact numbers, escaping of `"` `\`
and control characters only). Each C++ reader *normalizes*: it fills defaults, clamps, drops what
it does not know. "Round trip" therefore means: **parse + write in one language produces exactly
the bytes that parse + write produces in the other** (the canonical form), and the canonical form
is a fixed point in both.

| Format | Writer / reader | Shape | Normalization the Rust side must mirror |
|---|---|---|---|
| Trace `vigil-trace` 1 | `trace.cpp` | JSON lines: header, then one frame per line; short keys; player fields omitted at their default; 23 flag bits in `f` | Defaults for omitted keys; `double→int/float/uint8/uint32` casts; context outside 0..4 → Unknown; `\r` stripped; empty lines skipped |
| Outcome `vigil-outcome` 1 | `replay.cpp` | `{kind, format, frames, players{name:{suspicion, peak, evidence{}, detections{}}}}`, players and checks in byte order | suspicion/peak stored as `float`, written rounded to 2 decimals; `compareOutcomes` is the parity oracle |
| Marks `history/marks.json` 2 (1 readable) | `marks.cpp` | `{format, players{key:{…}}}`, keys sorted, indent 1 | Conditional fields (`confirmedAt` only when confirmed, …); `added` falls back to `confirmedAt`/`updated`; marks with no flag dropped; newer format → read-only |
| Profile `vigil-profile` 1 | `snapshot.cpp` | Player record, checks by **id**, evidence with values, detections, timeline, stats; indent 1 | Check/indicator ids resolved against the current catalog (unknown dropped and listed), output in catalog order; clamps (0–100, 0–1); bounds (600 evidence, 200 detections, 1500 timeline, 1440 history points, 16 values, 2000-byte strings) |
| Engine config / schema (P1) | `config.cpp` | `vigil-engine-config` 1, `vigil-engine-schema` 1 | Validation rules of `configFromJson` |

### 1.2 Byte-level facts that decide the design

* **Numbers**: integers below 1e15 as `%.0f`; otherwise `%.15g`, or `%.17g` when `%.15g` does not
  read back exactly; non-finite as `0`. Rust's shortest-representation formatting (`ryu`, used by
  `serde_json`) produces different text, so byte-identical output needs a printf-`%g` mirror.
* **Strings are bytes**: the C++ JSON layer neither validates nor requires UTF-8. Chat lines come
  from JNI `GetStringUTFChars` (*modified* UTF-8: supplementary characters as surrogate pairs, NUL
  as `C0 80`), so a real trace can contain bytes that are not valid UTF-8, and `\u` escapes of lone
  surrogates decode to such bytes. Profiles clip strings at 2000 *bytes*, which can split a
  character. A Rust model built on `String` would refuse or alter real files.
* **Parser leniency**: numbers go through `strtod`, which also accepts `+1`, `.5`, `1.`, `inf`,
  `nan` and hex floats. No Vigil writer produces these.
* **Line endings**: the committed trace files are LF (protected by the untracked `.gitattributes`);
  new fixtures may be checked out with CRLF, and every reader already tolerates `\r`.

### 1.3 Toolchain available

Rust 1.98.1, `x86_64-pc-windows-msvc`, with rustfmt and clippy; MSVC Build Tools for the C++ side.
No network is needed at build time if the crate has no dependencies.

## 2. Design

### 2.1 Workspace (`rust/`)

```
rust/Cargo.toml                 workspace (edition 2024), lints: unsafe_code = forbid
rust/rust-toolchain.toml        pinned 1.98.1 + rustfmt + clippy
rust/crates/vigil-formats/      library + binaries
  src/json.rs                   byte-exact mirror of core/json (parser, writer, %g numbers)
  src/trace.rs  outcome.rs  marks.rs  profile.rs  config.rs  catalog.rs
  src/bin/vigil-fmt.rs          canon <kind> <in> [out]: parse + write (the C++ tool's twin)
  src/bin/replay-check.rs       reads a trace and an outcome, checks them against each other
```

* **No third-party crates.** Byte-identical output requires a custom number formatter and byte
  strings anyway, which removes most of serde's value; zero dependencies also means no network,
  no supply-chain surface, and nothing to audit. `serde` can come when C++ writers are gone.
* JSON strings are `Vec<u8>` (`Text`), never `String`; the parser mirrors the C++ one decision for
  decision on every input Vigil can write (escapes, surrogate arithmetic with unsigned wrap,
  64-level depth limit, duplicate keys overwrite in place, insertion order kept).
* **Deliberate divergence**: Rust accepts only RFC 8259 numbers; it refuses the `strtod` extras.
  Classified as an *expected implementation difference* (stricter, never produced by a writer),
  documented and locked by a test.
* Casts mirror C++ for every in-range value (`as i32`, `as f32`, …); for out-of-range values C++
  is undefined behavior and Rust saturates (documented).
* `#![forbid(unsafe_code)]`; parsers return `Result`, never panic (checked by a mutation test).
* `CheckCatalog` (check and indicator ids in index order) is derived from the committed engine
  schema (P1), so profiles resolve ids exactly as the C++ engine of the same build does.

### 2.2 C++ side

* `tools/formats/formats.cpp` → **`VigilFormats`** (links only `vigil_detection`):
  `canon <kind> <in> <out>` (parse + write, the twin of `vigil-fmt canon`), `fixtures <dir>`
  (regenerates every generated fixture deterministically: no wall clock), `verdicts <dir>`.
* Fixtures in `tests/fixtures/formats/`: per format a C++-generated canonical file and hand-written
  inputs that exercise normalization (unknown checks, clamps, conditional fields, format 1 marks,
  hostile strings), each with its C++ canonical form; a table of 4 000+ doubles (text and bits) for
  the number formatter; a math table (`sin`, `cos`, `atan2`, `pow`, `sqrt`, `fmod`, … on the
  engine's input ranges) for the floating-point parity question of RUST_PLAN §8.

### 2.3 Round-trip protocol

For every fixture *f* of kind *k*:

1. **C++ → Rust**: `rust_canon(f)` equals the committed C++ canonical bytes.
2. **Rust → C++**: `cpp_canon(rust_canon(f))` equals `rust_canon(f)`.
3. **Fixed point**: `canon(canon(f)) = canon(f)` in both languages.
4. **Freshness**: `VigilFormats fixtures` regenerates byte-identical files (C++ determinism; the
   fixtures cannot drift from the C++ code).

(1) and (3) run in `cargo test` against committed files; (2) and (4) run in CI and locally with
both toolchains, also over the 7 corpus traces (≈ 4 900 frames, generated fresh, not committed).

## 3. Validation requirements

| # | Requirement | Method |
|---|---|---|
| W1 | P1 still holds | All suites, golden, `VigilParity` = P1 baseline, `engine-globals` |
| W2 | Rust parses every committed fixture | `cargo test` lists each fixture; the golden trace, its outcome and the P1 schema/config included |
| W3 | Round trips identical, both directions | §2.3 (1)–(4); corpus traces |
| W4 | Numbers byte-identical | Number table: Rust writes every double exactly like C++ and parses C++ text to identical bits |
| W5 | Hostile input | Same accept/refuse verdict as C++ on every hostile fixture (except the documented stricter numbers); a deterministic mutation test proves the Rust parsers never panic |
| W6 | `replay-check` | Passes on the golden trace + outcome; fails (exit 1, clear message) on a mismatched pair and on a corrupted trace |
| W7 | Toolchain quality gates | `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, all green; no `unsafe`, no dependencies |
| W8 | Falsification | Break the Rust number formatter, a default, a clamp; the fixture tests fail |
| W9 | No product change | Shipped targets build exactly as before; no file format version changes |

## 4. Exit criteria

1. Rust parses every committed fixture (W2) — RUST_PLAN.
2. C++ ↔ Rust round trips identical (W3, W4) — RUST_PLAN.
3. `replay-check` reads a trace and an outcome (W6) — RUST_PLAN scope.
4. W1, W5, W7, W8, W9 hold; divergences documented and classified.
5. CI runs the Rust gates and the cross-language round trips; RUST_PLAN §7, VALIDATION,
   ARCHITECTURE updated.

## 5. Roadmap

1. Workspace, toolchain pin, lints; `json` + number formatter with the number table first.
2. Trace, outcome, config/schema, catalog, marks, profile modules, each with fixtures as it lands.
3. `VigilFormats` (C++) and the committed fixture set; `vigil-fmt`; `replay-check`.
4. Cross-language round trips over fixtures and corpus traces; hostile verdicts; mutation test.
5. CMake option and CI job; falsification; documentation.

## 6. Risks

| Risk | Mitigation |
|---|---|
| printf `%g` rounding differs between MSVC's CRT and Rust's formatter | Number table of 4 000+ doubles (random bit patterns, halves, powers of two, integers near 1e15); any mismatch fails W4 |
| Rust readers silently diverge from C++ normalization | Hand-written inputs aimed at every default, clamp and bound, compared byte-for-byte with C++ canon |
| Fixtures drift from the C++ code | Freshness check (§2.3 (4)) in CI |
| CRLF checkouts break byte comparisons | Comparisons ignore `\r` in committed files; canonical output is LF |
| Two toolchains complicate the build | Rust is optional for the product build in P2; one documented command per side |

## 7. Out of scope

Any engine port (P3); linking Rust into the DLL, the C ABI, `catch_unwind` at FFI boundaries
(P4 — there is no FFI in P2); `cargo fuzz` (nightly-only; a deterministic mutation test stands in);
other files (`config.json`, `history/players.json`, session journals), which the Rust side does not
read yet.
